# bot-console: per-repo design (v2)

**Date:** 2026-10-13. **Status:** Draft, design only.
**Cross-repo design (the source of truth for auth, permissions, and the API):** [../../docs/design-bot-agent-deploy.md](../../docs/design-bot-agent-deploy.md). This file covers only what changes inside this repo.

## Direction

bot-console stops reading Postgres directly and becomes a BFF client of bot-api-server (decision D6). It holds no database login, no OAuth client secret, and no permission logic. It may hide controls the user's role cannot use, but bot-api-server decides.

## Transition

| Step | Pages | Data source | Status |
|---|---|---|---|
| Today | Overview, per-host, Services, Processes | `cluster_metrics` on pi4 via `src/lib/server/db.ts` (read-only login) | Superseded |
| v2 step 1 | Sign-in, projects, members, hosts, join tokens (new) | bot-api-server | Done |
| v2 step 2 | Overview, per-host, Services, Processes, page by page | bot-api-server `/v1/.../metrics` and `/health`, after bot-agent data is in `deploybot.metrics` | Done 2026-10-14 (Joe: old pages deleted) |
| v2 step 3 | Remove `src/lib/server/db.ts` and the `cluster_metrics` login from `.env` | — | Done 2026-10-14 (Joe: old pages deleted) |

Steps 2 and 3 landed together. The console no longer reads Postgres. Host overview and processes are tabs on `/hosts/[id]`. Services is a tab on `/projects/[id]`. Both are fed only by bot-api-server. `BOT_API_URL` is required.

## Auth (BFF)

- New routes: `/signin` (Google only for now; GitHub later), `/auth/google/callback`, `/signout`, `/device` (the device-code approval page for MCP clients: sign in, enter the code, approve; umbrella §7), `/oauth/consent` (MCP browser consent: client name marked unverified, full redirect host, Allow or Deny), `/account/apps` (Connected apps, linked from the header account menu, with a revoke action), and `/invite/[token]` (join a project from an invite link: lookup on load, Join posts accept, then 303 to that project).
- Sign-in: a server route calls bot-api-server `GET /v1/auth/google/start`, then redirects. The callback route posts `code` and `state` to `POST /v1/auth/google/callback` and receives the session token once.
- Cookie `bot_session`: `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age=604800`, and `Secure` when the origin is HTTPS (the dev `:5180` is HTTP over the tailnet, so no `Secure` there).
- `hooks.server.ts`: read the cookie, call `GET /v1/me` (cached for each request), and put the user in `event.locals`. Unauthenticated page requests redirect to `/signin`. `/api/*` returns 401. `safeNext` allows `/invite/<token>` only when the token is 43 base64url characters, with no query or extra segment. A signed-out `/invite/` request returns that redirect itself with `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, and `X-Frame-Options: DENY`. `/signin` responses send `Referrer-Policy: no-referrer` and `Cache-Control: no-store`, so `next` is not sent on to Google.
- Every server-side call to bot-api-server sends `Authorization: Bearer <cookie value>`. Each call also sets `X-Forwarded-For` to `event.getClientAddress()` when that value is an IP, and does not copy `X-Forwarded-For`, `Forwarded`, `X-Real-IP`, or other client-address headers from the caller. The browser never talks to bot-api-server.
- Mutating forms send one `idempotency_key` per click. Catalog run, stop, and restart keep the same key from the time the dialog opens until that post succeeds, and ignore a second click while it is in flight. A failed post retries with that key. After success the dialog mints a new key. Logs omit the key. SvelteKit's origin check covers CSRF for form POSTs.

## New pages

- **Projects:** list, create (the creator becomes owner), rename and delete (owner).
- **Project page loading:** each tab fetches only the lists it shows (Hosts: hosts; Services: hosts, then services; Catalog: hosts, members, catalog; Members: members, invites; Join tokens: join tokens; Settings: env sets, registries, files), after the project itself. Calls that do not depend on each other run in parallel; only Services waits for the host list. A failed list becomes that section's message. The catalog form asks for env-set names and file names with their own actions when the dialog opens. Those names are not loaded with the catalog tab.
- **Members:** list; admins add, remove, and change viewer/admin roles; the owner transfers ownership. Admin+ creates an invite link (viewer or admin, expiry 1, 7, or 30 days, uses 1, 5, or 25). The url is shown once in that dialog and is not put in the page URL, a cookie, or a log. Closing the dialog clears it; opening the dialog again shows the empty form. A url is shown only when its origin is this console's origin and its path is `/invite/<token>`. Pending invites list role, creator, expiry, uses, and status, and revoke with an icon-only Ban action.
- **Hosts:** per project: status (online, offline, or asleep for `always_on=false`), last seen, agent version; admin+ revokes a credential.
- **Join host:** admin+ creates a join token and sees it **once**, with the install command. The page never shows the token again.
- **Ops (phase 2):** logs for every member, viewers included. Deploy (by container name: adopt if it exists, create otherwise) for admin+. Run, stop, and restart for admin+ on `owned` services. Results come back inline. History reads `GET /v1/projects/{id}/audit`. This replaces the spec-v1 rule that "the dashboard does not drive ops".

## Env

`BOT_API_URL` is required. There is no Postgres URL or password. No OAuth secrets (they live on bot-api-server). An unset or invalid `BOT_API_URL` makes every route except static assets return 503.

## Components

Pages render on the server. JavaScript is required for dialogs, the theme switch, and chart refresh. Search, sort, paging, tabs, and filters stay in the URL, and every write is still a SvelteKit form action. Shared pieces live in `src/lib/components/` and are built on the shadcn-svelte primitives in `src/lib/components/ui/` (generated; do not edit them). Colours come only from the tokens in `src/app.css`. Icons are `@lucide/svelte`. `cn()` is in `src/lib/utils.ts`. Command lines, ports, pids, tokens, and install commands use the monospace stack. Dialogs mount only while open and use the generated portal.

| Piece | Role |
|---|---|
| `DataTable` | Every table. Client mode passes the rows the page already loaded. `src/lib/table.ts` sorts, searches (case-insensitive substring of searchable columns), and pages them from the URL: `<id>.q`, `<id>.sort`, `<id>.dir`, `<id>.page`. Sort headers and the pager are links. Search is a GET form. Default page size is 25. A table that fits on one page and has no search query shows no pager. The first click on a column uses that column's `firstDir` (ascending when omitted). A later click on the active column toggles. Server mode (`server` prop) does not sort, search, or page in the browser. The same namespaced params drive the API request. The pager says `Showing a–b of total`, and Prev/Next set `<id>.cursor`. A sort, search, or host change drops the cursor. A middle page, whose cursor is opaque, says `Showing n of total`. |
| `Tabs` | Link strip with `aria-current="page"` for the host page and the project page. |
| `PageHeader` | Breadcrumbs, `h1`, optional subtitle and actions. |
| `StatusBadge` | The known host and health statuses, plus `stopped` and `gone` for a service the host no longer reports. Anything else renders as `unknown`. |
| `Notice` | Error, info, and success text. Errors are alerts. The others are status. |
| `RowAction` | Icon-only ghost button for every action inside a table row. The `aria-label` and the tooltip are the action plus the row (for example "Rename port 22 · root"). Destructive rows use the destructive text colour. Rename is Pencil, probe Activity, revoke credential ShieldOff, remove member UserMinus, change role UserCog, revoke join token Ban, revoke invite Ban, delete Trash2. Catalog run is Play, stop Square, restart RotateCw, logs ScrollText, edit Pencil, permissions ShieldCheck, delete Trash2. Host approval is Check, and revoking an approval is Ban. Actions outside a table keep a text label. |
| `ConfirmAction` | Alert dialog for revoke credential, delete project, remove member, revoke join token, and revoke invite. The dialog holds the POST form (`ConfirmForm`). Inside a table row the trigger is a `RowAction`. Delete project asks the user to type the project name, and Confirm stays disabled until that text matches. The server still rejects a mismatch. No hidden field carries the project name. |
| `actionUrlFrom` | Named form actions on host and project pages. Keeps the current query, including table search, sort, and page, then appends `&/<name>`. |
| `backTo` | Success redirect for a same-page project action. Same path and query, minus `confirm` and the `/name` action key. |

Project services (`/projects/[id]?tab=services`, every member) call `GET /v1/projects/{id}/services` with `q`, `host_id`, `sort`, `dir`, `limit=25`, `cursor`, and `view`, taken from `services.q`, `services.host`, `services.sort`, `services.dir`, `services.cursor`, and `show`. Sortable columns are name, host, kind, status, and last seen (`last_seen` opens descending). Ports is not a sort. The Project column appears only when some row's `project_name` differs from this project. A Checks column lists health checks and posts the probe. Search is one server-side field. The host filter is a GET select of reachable hosts (relation owner, or shared at deploy), plus All hosts. A metrics share is not an option. A `services.host` that is not a UUID, or that is outside that set, is not sent, and the page shows a Notice. A cursor that is too long or contains a control character is not sent and shows a Notice. A search longer than 100 characters after trimming, or one that contains NUL, is not sent and shows a Notice. It is not treated as an empty search. The Show select sits with the host filter. Changing either select submits the form at once; there is no Apply button. `show=deploybot` (the default, also used when `show` is missing or unknown) sends `view=deploybot`. `show=discovered` sends `view=deploybot_and_discovered`. `show=all` sends `view=all`. Paging, search, and sort keep `show`. The host form writes that one `show` and still drops the cursor. A row with `gone_at` set shows stopped (owned or declared) or gone (discovered) instead of the health status. The default view with no rows, no search, and no load or action message says "No services run by deploybot yet." and links to `show=discovered` on the same project, keeping `services.host`. A search with no hits, or a message, keeps "No services reported." The rename form renders only when that row may be renamed. `serviceLabel` is `display_name`, otherwise the discovered name, unless that name is `port-<n>`, which renders as `port <n> · <owner_user>`. Admin+ renames from an icon button on the row. The dialog posts `display_name` (at most 64 characters) to the shared `rename` action, which still `PATCH`es `/v1/services/{id}`. A failed rename shows a Notice and keeps the typed value. Probe on that row is an icon button too. The process sample is still `sort=cpu|memory` and `limit=200`, and the processes table opens descending. CPU, RSS, memory, and threads also open descending when chosen from another column. The Process cell shows `process_name`. A Service column shows that label (or the word `service`) and links to the service's project only when the caller is a member of it. The link's `services.q` is the discovered name, capped at 100 code points.

Project catalog (`/projects/[id]?tab=catalog`, every member) lists `GET /v1/projects/{id}/catalog`. Columns are name, command (`command_display`, monospace), run as, and port. A container port is `<host>:<container>`, or `<host>:<container> public` when it is public. Row actions are only the entry's `my_actions`: Run, Stop, Restart, and Logs. Each opens a dialog with a host select of owned hosts and deploy shares. A host with no program policy, with programs disabled, without the entry's `run_as`, or (for a shell entry) without `allow_shell`, is listed and disabled with the reason. The same reason is shown under the select. Run, stop, and restart post `{host_id, idempotency_key}` and reuse that key until the post succeeds. Logs post `{host_id}` only. The new-service, edit, and run dialogs limit their height to the viewport and scroll the body. A status line shows the ProgramStatus. The message `waiting for the host owner's approval` is an info Notice. Logs render as text in a scrollable monospace block. The owner also gets New service and Container (page header), Edit, Permissions, and Delete. Delete warns that running units are not stopped. New and Edit are a program form: name (create only), working directory, one command line, "Run through a shell" (the risk line `anything in this line runs as <run_as>`, shown once a run-as account is chosen), run as chosen from the union of `run_as` on eligible hosts, expected port, environment rows, and restart. A debounced Preview posts the command to `POST /v1/projects/{id}/catalog/parse` and shows `will run:` plus the argv, or the API refusal. Leading assignments from that preview are added to the environment rows. Saving does not drop its own result when a preview is still in flight. The API refuses environment keys that change what the program runs; the form shows that message and does not keep its own copy of the denylist. Permissions is a GET `?tab=catalog&permissions=<name>` section in the page, so the form is in the server HTML. Cancel returns to the catalog URL without `permissions`. The section has Admins, Viewers, and per-member checkboxes for run, stop, restart, and logs, saved with PUT. The console does not send `secret_env`.

Settings, for an owner or admin, lists project files with name, secret or plain, size, and updated time. Add or replace posts a name, a paste box, and a secret flag that defaults to on. The paste box is never pre-filled, is cleared after a save, has `autocomplete="off"`, and is not put in the URL. A plain file can be viewed in a read-only block, and focus moves to that block. A secret file has no view action. Delete confirms. A conflict closes the dialog and shows the API message on that file's row, naming the entries that still use the file. An API error is shown without the file content.

A container form has a port row for each published port, with Public (all interfaces) off by default. A public port listens on all of the host's interfaces and is allowed only when that host's runner.toml sets `allow_public_ports = true`; otherwise the deploy is refused. The read-only preview shows `-p <host>:<container>` for a public port and `-p 127.0.0.1:<host>:<container>` otherwise. The catalog port column and the deploy dialog use that same `<host>:<container> public` marking. The dialog shows the port line before Deploy (Run job for a job), and adds `Publishes on all of the host's interfaces.` when any port is public. The form also has file rows: a select of that project's files and a target path. The client checks v1.9 rule 13 (at most 16, each file once, an absolute target that is not `/`, `/proc`, `/sys`, `/dev`, or under them, and no target shared with or nested under a volume). The API remains authoritative for whether the file exists. Editing an entry keeps its rows. The read-only `docker run` preview adds a shell-quoted `-v <file>:<target>:ro` for each row. Pasting a `docker run` line does not invent file rows. When the chosen host's `programs.files` is not true and the entry has files, the deploy dialog says "This host's agent does not support files" and does not offer Deploy for that host. An entry with no files can still deploy there. Rollback and remove stay available. A successful container save closes the dialog and, after that dialog has finished closing, the catalog shows a success Notice, `Saved <name>.`, which wraps a long name. A failed save leaves the dialog open with the error. Loading env sets or files does not close the dialog and does not clear the notice. The notice clears when the project changes, when the tab leaves Catalog, when Permissions opens, when the user deletes, runs, stops, restarts, deploys, or rolls back, or when a create or edit dialog opens. A save cancelled before it is sent does not clear it. A later save shows it again.

Host catalog approvals (`GET /v1/hosts/{id}/catalog-approvals`) render under both host tabs for an admin or owner of the host's owning project. Columns are project, entry, command, exec, args, env, dir, run as, shell, requested by, and status. Env is `KEY=value` lines. Approve posts the shown `spec_hash`. Revoke confirms, then deletes that approval. Anyone else does not see the section. A list error stays on that section.

`tests/components-reuse.test.ts` rejects a route that grows its own table, tab strip, alert, `confirm(`, `StatusText` import, or `<h1`. It also rejects a `#hex`, `rgb(`, `oklch(`, or `color-mix(in oklch` literal and an inline colour style (`style=` or `style:`) outside `src/lib/components/ui/`, `forceMount` or `portalProps` outside that folder, a text-labelled button inside a DataTable row snippet, and a raw `<button` or `<input` outside `src/lib/components/ui/` and `src/lib/components/*.svelte`.

## Theme

Cookie `bot_theme` is `system` (the default), `light`, or `dark`. Any other value counts as `system` and is never written back raw. `POST /theme` is public. It sets the cookie (`HttpOnly`, `SameSite=Lax`, `Path=/`, max-age one year, `Secure` only when the request is https) and redirects to a safe `next`, or to `/` when `next` is unsafe. The server writes `class="dark"` for dark, nothing for light, and `data-theme="system"` for system. An inline script in `src/app.html` (`nonce="%sveltekit.nonce%"`) adds `.dark` before paint when the choice is system and the OS prefers dark, and it follows later OS changes only while that attribute is still `system`. `ThemeSwitch` sets the class immediately, then posts `/theme` (`name="theme"`, hidden `next`) with `use:enhance` and does not reload the page. At 640 px and below the three choices are icons only, and the switch sits on the next header line. The signed-in row wraps, and a long account name truncates.
