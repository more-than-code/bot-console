# bot-console

SvelteKit console for Deploybot. It is a BFF in front of bot-api-server: the browser never calls the API, and this app has no database login. Sign in with Google, then open a project and a host. A project has a Services tab. A host has Overview and Processes tabs.

JavaScript is required. Search, sort, paging, tabs, and filters stay in the URL. Writes are SvelteKit form actions. Brand files (favicons, apple-touch and manifest icons, header lockups) are copied from the umbrella `docs/brand/logo/` into `static/brand/`; `static/manifest.webmanifest` lists the app icons. The UI is Tailwind CSS v4 and shadcn-svelte (style `nova`, neutral base, Lucide icons). `cn()` lives in `src/lib/utils.ts`. Colours are the tokens in `src/app.css` (light on `:root`, dark on `.dark`), including the Deploybot status tokens. The header theme switch posts to `/theme` and stores `bot_theme` (`system`, `light`, or `dark`; default `system`).

## Setup

Requires Node.js 20+ and pnpm:

```bash
pnpm install
```

Copy `.env.example` to `.env`. The app reads these variables on the server only (`$env/dynamic/private`):

| Key | Purpose |
|-----|---------|
| `BOT_API_URL` | Required bot-api-server origin, no path. Unset or invalid → 503 `Console is not configured (BOT_API_URL)` |
| `BOT_API_ALLOW_INSECURE_HTTP` | Set to `1` to allow a non-loopback `http://` API URL (development/internal testing only) |
| `BOT_API_OAUTH_AUTHORIZE_HOSTS` | Comma-separated `authorize_url` hostnames. Default `accounts.google.com` |

`https` is accepted. `http` is accepted only for `localhost`, `127.0.0.1`, and `::1`, unless `BOT_API_ALLOW_INSECURE_HTTP=1`.

Do not commit `.env`. `.env` is gitignored.

`vite dev` and `vite preview` load `.env` themselves. `node build` does not, so export the variables or run with the working directory set to this repo. A systemd `EnvironmentFile=` is the better production source.

## Scripts

| Script | What it does |
|--------|----------------|
| `pnpm dev` | Dev server on `0.0.0.0:5180` (`strictPort`) |
| `pnpm build` | Production build into `build/` |
| `pnpm preview` | Preview the build on `0.0.0.0:5180` |
| `pnpm check` | `svelte-check` |
| `pnpm test` | Unit tests (`node --test`). They mock `fetch`. There is no API server in the tests. |

Production, behind the reverse proxy:

```bash
PORT=5180 HOST=127.0.0.1 ADDRESS_HEADER=X-Forwarded-For XFF_DEPTH=1 node build
```

`PORT` defaults to 3000 and `HOST` to `0.0.0.0` in the Node adapter. Bind to loopback (`HOST=127.0.0.1`) when a reverse proxy is the only client. `ADDRESS_HEADER=X-Forwarded-For` and `XFF_DEPTH=1` make `event.getClientAddress()` the rightmost forwarded address, the one the closest proxy added. The console sets that address as `X-Forwarded-For` on every bot-api-server call. The API rate-limits Google sign-in start (20 per minute), invite redemption, and OAuth by client IP, and it uses the rightmost `X-Forwarded-For` address only when the TCP peer is `BOT_API_TRUSTED_PROXY` (`127.0.0.1` in production). Without the header, every console user shares that loopback bucket. A client who can reach the console directly can spoof `X-Forwarded-For`, which is why the process listens on loopback. `vite dev` ignores these two variables and uses the socket peer. If `getClientAddress()` throws, or returns an empty or non-IP value, the console sends no `X-Forwarded-For`.

In development, run `pnpm dev` on port 5180 against a running `bot-api-server` (e.g. `BOT_API_URL=http://127.0.0.1:8090`).

The container form's Image field is a combobox (api-v1 v1.16) that still takes any typed or pasted reference, including `@sha256:` digests, and saves it as typed. While the field has focus, the console asks the API for the registry's tags of the repository part (400 ms after it last changed, once per repository while the dialog is open; a timeout, rate limit, unreachable registry or bad answer is asked again on the next focus) and lists up to 50 of them filtered on the text after `:`, with `N more, type to filter` under the list and `Loading tags…` under the field while they load; a screen reader hears the same through a polite status region. Picking a tag (arrow keys and Enter, or a click; Enter without moving to an option leaves the text as typed) sets `<repo>:<tag>`, then asks for that tag's digest and, if the field has not changed meanwhile, pins it as `<repo>:<tag>@sha256:…` with the line `Pinned to sha256:<12 hex>…` (a pinned value over 255 bytes is not written); deleting the `@sha256:…` part follows the tag again. A failed digest keeps `<repo>:<tag>` and says `Could not pin a digest; the tag will be used.` A failed tag lookup shows one line under the field (an unknown registry, refused stored credentials with a link to Settings → Registries that opens in a new tab, an image that is missing or private, an unreachable registry, or `Could not load tags.`); none of them blocks saving. Against an older API (404) the field behaves as a plain input with no message.

Security note: The console dashboard is intended to run behind an authenticating reverse proxy with TLS or on private/overlay networks (VPN/internal). Do not expose the HTTP port directly to untrusted networks.

## Auth

`BOT_API_URL` is required. Every page except `/about`, `/privacy`, `/terms`, `/signin`, `/theme`, `/auth/google/callback`, and static assets needs a session. The signed-in app shell has a footer with Privacy and Terms links. A page without a session redirects to `/signin?next=<path>`, and `next` has to be a same-origin relative path.

Sign-in is one "Sign in with Google" button. The server asks bot-api-server for the Google URL, stores the OAuth `state` and `next` in a short-lived HttpOnly cookie, and sends the browser to `authorize_url`. That redirect happens only when the URL is `https` and its parsed hostname is in `BOT_API_OAUTH_AUTHORIZE_HOSTS`. The callback checks `state`, posts the code to `/v1/auth/google/callback`, and stores the API token in the `bot_session` cookie. That cookie is HttpOnly, SameSite=Lax, Path=/, Max-Age 604800, and `Secure` only when the console request itself is https. The browser does not receive the session token in a response body.

`/signout` asks the API to delete the session and always clears the cookie. Mutations are form posts to this app. The server calls bot-api-server.

A join token is shown once, on the create result, and is not written to browser storage. The API install command is not shown. The page shows `sudo ./install.sh enroll --server '<server>' --runner` instead, with `<server>` taken from that command (plus `--insecure-dev` when that server is `ws://` on `127.0.0.1` or `localhost`, the only `ws://` the agent accepts), and tells the admin to paste the join token at the hidden prompt. The token is not in the command or its copy button. If the command is missing, not the expected form, or its server value contains the token, the page says `Server URL not shown: unexpected format` and the enrol command uses `<your server URL>`. An invite link is the same kind of one-time secret: admin+ creates it on the Members tab, the dialog shows the url once, and closing the dialog clears it. The url is shown only when its origin is this console and its path is `/invite/<token>`. The pending list never includes the token. Opening the link does not join; Join is a POST. `/signin` responses send `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. Buttons follow the caller's project role. The API still enforces that role. `forbidden` and `not_found` are messages on the page. Lists that stop at the page or item cap, or that see a repeated cursor, say `More items not shown`.

The header shows the Deploybot lockup (light or dark to match the theme; it links to `/projects`), a Projects link, the theme switch (System, Light, Dark), and, when signed in, the user's Google avatar left of their name (only an `https` URL is used, loaded with no referrer; without one, or if it fails to load, a circle with the name's first letter), a menu linking to Connected apps, and Sign out.

This console has not been run against bot-api-server or Google from the unit tests. They mock `fetch`.
